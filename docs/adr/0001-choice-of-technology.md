# ADR-001: Вибір брокера повідомлень для подієво-керованої взаємодії — Apache Kafka замість RabbitMQ

## Context

Vectix є розподіленою системою, у якій оформлення замовлення (Saga) та відстеження вантажу ґрунтуються на асинхронному обміні подіями між мікросервісами. Вимоги SRS накладають такі обмеження на брокер:

- прийом не менше 1000 подій відстеження за секунду ([SRS-NFR-PERF-03](../srs.md#srs-nfr-perf-03));
- впорядкування подій одного вантажу та дедуплікація перед оновленням read-model ([SRS-FUN-16](../srs.md#srs-fun-16));
- відсутність втрати подій та ідемпотентна обробка ([SRS-NFR-CONS-01](../srs.md#srs-nfr-cons-01));
- можливість перебудови CQRS read-model Tracking Service з історії подій.

Необхідно обрати брокер, що забезпечує зазначені властивості в межах ресурсів дипломного проєкту (розгортання в Docker Compose та Kubernetes).

## Alternatives

**Альтернатива 1. RabbitMQ (AMQP 0-9-1).** Брокер із чергами, гнучкою маршрутизацією (exchanges) та підтвердженням доставки на рівні повідомлення. Повідомлення після підтвердження видаляється з черги, тому відтворення історії подій для перебудови read-model потребує окремого сховища або використання RabbitMQ Streams. Порядок гарантується в межах однієї черги з одним споживачем; паралельна обробка кількома споживачами порушує порядок. Операційна складність нижча, ніж у Kafka.

**Альтернатива 2. Apache Kafka.** Розподілений журнал подій із партиціями та групами споживачів. Повідомлення зберігаються протягом заданого періоду незалежно від споживання, що дозволяє повторне відтворення. Порядок гарантується в межах партиції; ключ партиціювання (shipment_id) забезпечує впорядкування подій одного вантажу при паралельній обробці різних вантажів. Гарантія доставки за замовчуванням at-least-once.

**Альтернатива 3. Прямі синхронні виклики gRPC без брокера.** Відхилена: не розв'язує сервіси в часі, не усуває каскадних відмов та не забезпечує буферизації пікового навантаження, що суперечить [SRS-NFR-REL-01](../srs.md#srs-nfr-rel-01).

## Decision

Обрано Apache Kafka (режим KRaft, без ZooKeeper) як єдиний брокер подій. Ключові аргументи:

1. Збереження журналу подій дає змогу перебудовувати CQRS read-model Tracking Service відтворенням топіка без додаткового сховища.
2. Партиціювання за ключем shipment_id забезпечує впорядкування подій одного вантажу при горизонтальному масштабуванні споживачів ([SRS-FUN-16](../srs.md#srs-fun-16)).
3. Групи споживачів дозволяють незалежне споживання тих самих подій кількома сервісами (Tracking, Notification, Document) без дублювання топіків.
4. Цільова пропускна здатність 1000 подій за секунду досяжна обома брокерами; пропускна здатність не є вирішальним критерієм вибору.

Рішення приймається за умови застосування Transactional Outbox у сервісах-публікаторах та Idempotent Consumer у споживачах.

## Consequences

**Позитивні:**

- Можливість повторного відтворення подій для відновлення read-model та діагностики інцидентів.
- Збереження порядку подій в межах вантажу при паралельній обробці.
- Незалежне масштабування споживачів через групи споживачів.
- Брокер має відкритий протокол і не створює Vendor Lock-in; наявні керовані пропозиції у хмарних провайдерів.

**Негативні та ризики:**

- Вища операційна складність порівняно з RabbitMQ: необхідні налаштування реплікації, retention, партицій та моніторингу consumer lag.
- Більше споживання ресурсів: у середовищі розробки Kafka вимагає більше пам'яті, ніж RabbitMQ, що збільшує вимоги до локальної інфраструктури та CI.
- Відсутність вбудованої гнучкої маршрутизації та відкладеної доставки: сценарії затримки (наприклад, таймаут Saga) потребують окремої реалізації.
- Гарантія at-least-once вимагає ідемпотентності всіх споживачів, що ускладнює код та тестування.
- Кількість партицій складно зменшити після створення; помилка вибору призводить до перебалансування або міграції топіків.
- FinOps: використання керованого Kafka у хмарі економічно менш вигідне за невеликого навантаження, ніж RabbitMQ; у межах диплому використовується самостійне розгортання в Kubernetes та Docker Compose.
- Eventual Consistency між write-моделлю та read-моделлю потребує проєктування UX та моніторингу затримки ([SRS-NFR-CONS-01](../srs.md#srs-nfr-cons-01)).

**Заходи пом'якшення:** режим KRaft з одним брокером для розробки та трьома для демонстрації відмовостійкості; експорт метрик consumer lag у Prometheus; стандартизований шаблон Idempotent Consumer у спільному пакеті Turborepo; початкова кількість партицій топіка tracking.events — 6.
