## 1. System Context (Контекст системи)

### 1.1. Межі системи (Scope)

Vectix забезпечує прийом вантажних запитів відправників, формування та ранжування пропозицій перевізників, оформлення замовлення на перевезення, відстеження вантажу та формування супровідних документів для напряму Китай — Україна. Система складається з двох порталів (Client Portal, Carrier Portal) та набору мікросервісів, що взаємодіють через REST, gRPC та Apache Kafka.

**У межах системи:** автентифікація та авторизація, розрахунок тарифікованої ваги, агрегація пропозицій, Saga оформлення замовлення, відстеження подій, документи та сповіщення, рейтинг перевізників.

**За межами системи:** фізичне виконання перевезення, митне оформлення, розрахунки між перевізником і банком, внутрішні системи перевізників.

### 1.2. Зовнішні інтерфейси

| Зовнішня сутність | Тип | Взаємодія |
| --- | --- | --- |
| Client (відправник) | Користувач | Client Portal, REST / HTTPS, SSE / HTTPS |
| Carrier Operator | Користувач | Carrier Portal, REST / HTTPS |
| Admin | Користувач | Carrier Portal (адміністративна роль), REST / HTTPS |
| Carrier APIs | Зовнішні системи | Отримання тарифів: REST / HTTPS; прийом подій статусу: webhooks / HTTPS |
| Payment Provider | Зовнішня система | Утримання та повернення коштів: REST / HTTPS |
| Insurance Provider | Зовнішня система | Розрахунок премії та оформлення поліса: REST / HTTPS |
| Email та Telegram | Зовнішні системи | Доставка сповіщень: SMTP / TLS, Bot API / HTTPS |

## 2. Functional Requirements (Функціональні вимоги)

### 2.1. Identity & Access

#### SRS-FUN-01

Система повинна реєструвати користувача з однією з ролей: Client, Carrier, Admin.

#### SRS-FUN-02

Система повинна автентифікувати користувача за протоколом OAuth 2.0 / OIDC та видавати підписаний JWT-токен доступу.

#### SRS-FUN-03

Система повинна обмежувати доступ до ресурсів відповідно до ролі користувача (RBAC) на API Gateway та на рівні кожного сервісу.

### 2.2. Shipment Request

#### SRS-FUN-04

Система повинна приймати та валідувати вантажний запит, що містить маршрут, кількість місць, габарити та вагу кожного місця, категорію вантажу, код HS, декларовану вартість та Incoterm.

#### SRS-FUN-05

Система повинна розраховувати тарифіковану вагу як максимум між фактичною та об'ємною вагою, де об'ємна вага дорівнює добутку довжини, ширини та висоти в сантиметрах, поділеному на коефіцієнт перевізника.

### 2.3. Quote Engine та Scoring

#### SRS-FUN-06

Система повинна формувати пропозиції перевізників паралельно за тарифними сітками та через адаптери зовнішніх API.

#### SRS-FUN-07

Система повинна повертати часткові результати, якщо відповідь окремого перевізника не отримано в межах таймауту або Circuit Breaker цього перевізника перебуває у стані open.

#### SRS-FUN-08

Система повинна ранжувати пропозиції за зваженою сукупністю критеріїв: ціна, строк, рейтинг перевізника, надійність.

#### SRS-FUN-09

Система повинна прогнозувати строк доставки (ETA) для кожної пропозиції за історичними даними виконаних замовлень.

### 2.4. Carrier Management

#### SRS-FUN-10

Система повинна надавати перевізнику керування тарифними сітками, маршрутами та місткістю через Carrier Portal.

#### SRS-FUN-11

Система повинна надавати перевізнику можливість приймати або відхиляти замовлення.

### 2.5. Order Orchestrator

#### SRS-FUN-12

Система повинна виконувати Saga оформлення замовлення у послідовності: резервування місткості, страхування, утримання коштів, підтвердження перевізником.

#### SRS-FUN-13

Система повинна виконувати компенсуючі транзакції виконаних кроків Saga у зворотному порядку, якщо будь-який крок завершився відмовою.

#### SRS-FUN-14

Система повинна обробляти повторний запит на оформлення замовлення з однаковим ключем ідемпотентності без створення дубльованого замовлення.

### 2.6. Tracking

#### SRS-FUN-15

Система повинна приймати події статусу вантажу та публікувати їх у Apache Kafka.

#### SRS-FUN-16

Система повинна виконувати дедуплікацію подій за ідентифікатором події та впорядкування за часовою позначкою перед оновленням CQRS read-model.

#### SRS-FUN-17

Система повинна доставляти клієнту оновлення статусу вантажу через SSE.

### 2.7. Documents, Notifications, Rating

#### SRS-FUN-18

Система повинна генерувати накладну та рахунок у форматі PDF та зберігати їх у S3-сумісному сховищі.

#### SRS-FUN-19

Система повинна надсилати користувачу сповіщення про зміну статусу замовлення електронною поштою або через Telegram.

#### SRS-FUN-20

Система повинна обчислювати рейтинг перевізника за результатами виконаних замовлень.

### 2.8. Compliance та аудит

#### SRS-FUN-21

Система повинна видаляти або анонімізувати персональні дані користувача за його запитом.

#### SRS-FUN-22

Система повинна реєструвати в журналі аудиту дії автентифікації, зміни тарифів та зміни стану замовлення.

## 3. Non-Functional Requirements (Нефункціональні вимоги)

### 3.1. Продуктивність та масштабованість

#### SRS-NFR-PERF-01

Час відгуку API (Latency) на 95-му перцентилі (p95) має не перевищувати 200 мс при навантаженні 500 RPS для всіх ендпоінтів, окрім генерації пропозицій.

#### SRS-NFR-PERF-02

Час генерації пропозицій на p95 має не перевищувати 3 с при навантаженні 100 RPS; таймаут запиту до одного перевізника має дорівнювати 2 с.

#### SRS-NFR-PERF-03

Tracking Service повинен приймати не менше 1000 подій відстеження за секунду; затримка доставки статусу клієнту на p95 має не перевищувати 2 с.

#### SRS-NFR-SCAL-01

Stateless-сервіси повинні мати не менше 2 реплік та масштабуватися горизонтально (HPA) при перевищенні середнього завантаження CPU 70%.

### 3.2. Консистентність

#### SRS-NFR-CONS-01

Затримка оновлення CQRS read-model має не перевищувати 5 с; втрата подій не допускається (Transactional Outbox); повторна обробка дубліката події не повинна змінювати стан системи.

#### SRS-NFR-CONS-02

Компенсація Saga повинна завершуватися за час не більше 30 с; замовлення не повинно перебувати в проміжному стані довше 5 хв.

### 3.3. Надійність

#### SRS-NFR-REL-01

Доступність системи має становити не менше 99,9% на місяць (допустимий простій до 43,8 хв).

#### SRS-NFR-REL-02

Circuit Breaker повинен переходити у стан open, якщо частка помилок досягає 50% у вікні з 20 запитів, та переходити у стан half-open через 30 с.

#### SRS-NFR-REL-03

Цільові показники відновлення: RPO не більше 5 хв (WAL archiving), RTO не більше 30 хв; повне резервне копіювання PostgreSQL повинно виконуватися щодоби зі зберіганням 7 діб.

### 3.4. Безпека та комплаєнс

#### SRS-NFR-SEC-01

Автентифікація повинна ґрунтуватися на OAuth 2.0 / OIDC; JWT повинні бути підписані алгоритмом RS256; TTL токена доступу має становити 15 хв, TTL refresh-токена — 7 діб із ротацією.

#### SRS-NFR-SEC-02

Зовнішні канали повинні використовувати TLS не нижче версії 1.2; паролі повинні зберігатися у вигляді хешу Argon2id; секрети не повинні зберігатися в репозиторії.

#### SRS-NFR-SEC-03

API Gateway повинен застосовувати Rate Limiting за алгоритмом Token Bucket: 100 запитів за хвилину на клієнта.

#### SRS-NFR-SEC-04

Образи релізу не повинні містити вразливостей рівня CRITICAL та HIGH за результатами Trivy; система має відповідати OWASP Top 10.

#### SRS-NFR-SEC-05

Обробка персональних даних повинна відповідати принципу мінімізації; видалення або анонімізація за запитом має виконуватися не більше ніж за 30 діб (GDPR, Закон України «Про захист персональних даних»); дані платіжних карток не повинні зберігатися в системі (PCI DSS).

#### SRS-NFR-SEC-06

Кожен публічний ендпоінт повинен мати схему валідації вхідних даних (DTO); SQL-запити повинні виконуватися лише з параметризацією.

### 3.5. Якість, спостережуваність, розгортання

#### SRS-NFR-QUAL-01

Покриття модульними тестами доменної логіки має становити не менше 80%; SonarQube Quality Gate повинен проходитися з 0 Blocker та 0 Critical проблем і часткою дублювання не більше 3%.

#### SRS-NFR-OBS-01

100% міжсервісних запитів повинні мати наскрізний trace-id (OpenTelemetry); метрики RED повинні збиратися в Prometheus; сповіщення повинно ініціюватися при частці помилок понад 1% за 5 хв.

#### SRS-NFR-DEP-01

Усі сервіси мають бути контейнеризовані (Docker); повний CI/CD-конвеєр (GitHub Actions) має виконуватися за час не більше 15 хв.

## 5. Glossary (Глосарій)

| Термін | Визначення |
| --- | --- |
| Saga | Патерн розподіленої транзакції у вигляді послідовності локальних транзакцій із компенсуючими діями на випадок відмови наступного кроку |
| Transactional Outbox | Патерн, за якого подія записується в таблицю outbox тією ж локальною транзакцією, що й зміна стану, та публікується в брокер окремим процесом |
| Idempotent Consumer | Споживач повідомлень, повторна обробка одного повідомлення яким не змінює стан системи |
| CQRS | Command Query Responsibility Segregation: розділення моделей обробки команд і читання даних |
| Eventual Consistency | Модель узгодженості, за якої дані в різних сховищах стають узгодженими після скінченного інтервалу часу |
| Тарифікована вага (Chargeable Weight) | Вага, за якою перевізник розраховує вартість: максимум між фактичною та об'ємною вагою |
| p95 Latency | Час відгуку, який не перевищується у 95% запитів |
