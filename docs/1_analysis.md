## 1.2. Аналіз існуючих аналогів

Для порівняльного аналізу обрано три програмні системи, що вирішують суміжні задачі
агрегації пропозицій перевізників, оформлення відправлень і відстеження вантажів:
Freightos (WebCargo), Flexport та Shippo. Аналіз виконано з позицій системної архітектури,
протоколів взаємодії, стеку даних та відомих обмежень. Джерелами слугували публічна
документація API та опубліковані технічні вимоги до інженерних вакансій розробників.
Внутрішні деталі реалізації комерційних систем публічно не розкриваються, тому відсутні у
відкритих джерелах параметри позначено в таблиці як недокументовані.

### 1.2.1. Freightos (WebCargo)

**Архітектурний патерн.** За даними технічних вимог до вакансій, платформа складається з
PHP-застосунків із клієнтською частиною на React; зазначається необхідність знання
мікросервісної інфраструктури. Одночасно задекларовано рефакторинг кодової бази відповідно
до принципів SOLID, DDD та Hexagonal Architecture, що вказує на наявність застарілих
монолітних компонентів, які підлягають поступовій декомпозиції.

**Протоколи та стек даних.** Публічна документація внутрішніх протоколів взаємодії
відсутня. Як СУБД згадується MySQL.

**Технічні обмеження.** Співіснування застарілих PHP-компонентів і нової мікросервісної
інфраструктури створює технічний борг та ускладнює горизонтальне масштабування окремих
підсистем. Платформа оперує значними обсягами тарифних даних (мільйони тарифних точок і
сотні тисяч котирувань у публічних матеріалах компанії), що висуває вимоги до
продуктивності розрахунку пропозицій.

### 1.2.2. Flexport

**Архітектурний патерн.** Відповідно до опублікованих технічних вимог, система мігрує з
монолітної архітектури на основі Ruby on Rails до мікросервісів на Kotlin, що
розгортаються в Kubernetes. Клієнтська частина реалізована на React із поступовим
переходом до TypeScript.

**Протоколи та стек даних.** Для обміну даними застосовуються GraphQL (клієнт Relay) та
gRPC, для асинхронної взаємодії — Apache Kafka. Транзакційні дані зберігаються в
PostgreSQL (AWS RDS), аналітичні — у Snowflake. Інфраструктура розгортається в AWS.

**Технічні обмеження.** Одночасна експлуатація Rails-моноліту та мікросервісів зумовлює
тимчасову гетерогенність стеку (Ruby, Kotlin, TypeScript), підвищує складність
спостережуваності та супроводу. Механізми забезпечення узгодженості даних між сервісами
(Saga, Outbox) у відкритих джерелах не описані.

### 1.2.3. Shippo

**Архітектурний патерн.** Shippo реалізує API-first агрегаційний шар над API перевізників
(USPS, UPS, DHL та інших): єдиний інтерфейс для розрахунку тарифів (rate shopping),
придбання етикеток і відстеження посилок. Внутрішня архітектура публічно не розкрита.

**Протоколи та стек даних.** Публічне API побудовано за принципами REST з автентифікацією
за токеном (HTTP Authentication). Сповіщення про події відстеження та транзакцій надаються
через webhooks. СУБД у відкритих джерелах не вказано.

**Технічні обмеження.** URL для webhooks конфігурується через панель керування, а не
програмно. За відсутності webhooks необхідно виконувати polling ендпоінту відстеження.
Доступність даних відстеження залежить від можливостей конкретного перевізника. API
застосовує обмеження частоти запитів (Rate Limiting). Система орієнтована на посилки
електронної комерції та не охоплює вибір перевізника для міжнародних вантажних перевезень
з розподіленим життєвим циклом замовлення.

### Аналітичний висновок підрозділу 1.2

Аналіз показав, що Freightos та Flexport перебувають у процесі декомпозиції монолітних або
гетерогенних кодових баз у мікросервісну архітектуру, що супроводжується технічним боргом,
співіснуванням кількох технологічних стеків та ускладненням спостережуваності. Shippo
забезпечує уніфікований доступ до перевізників за REST та webhooks, однак орієнтований на
агрегацію тарифів і етикеток для посилок і не містить публічно описаного механізму
розподіленого оформлення замовлення. Залежність відстеження від можливостей перевізників
та необхідність polling за відсутності webhooks обмежують повноту даних у реальному часі.
У відкритих джерелах щодо аналізованих систем відсутні відомості про застосування патернів
розподіленої узгодженості (Saga, Transactional Outbox, Idempotent Consumer), що залишає
питання консистентності даних між операціями резервування місткості, страхування та оплати
поза межами публічної документації.

У межах кваліфікаційної роботи для вирішення виявлених обмежень передбачено проєктування
Vectix як Event-Driven мікросервісної системи з початку життєвого циклу, без перехідного
монолітного шару. Узгодженість розподіленого оформлення замовлення забезпечується
оркестрованою Saga з компенсуючими транзакціями; надійна публікація подій — Transactional
Outbox; стійкість до повторної доставки повідомлень Apache Kafka — Idempotent Consumer;
ізоляція збоїв зовнішніх API перевізників — Circuit Breaker. Розділення моделей запису і
читання (CQRS) у модулі відстеження дає змогу незалежно масштабувати прийом подій і
доставку статусів клієнту. Використання Turborepo для єдиного монорепозиторію забезпечує
спільні пакети типів та контрактів між NestJS-сервісами та клієнтом на Next.js, а
виділення Python-сервісу на FastAPI ізолює обчислювальне навантаження скорингу пропозицій
та прогнозування ETA від бізнес-сервісів.

Обраний підхід передбачає компроміс: Database per Service та асинхронна взаємодія
забезпечують ізоляцію й масштабованість, але допускають лише Eventual Consistency, що
потребує проєктування компенсуючих сценаріїв і розширеної спостережуваності
(OpenTelemetry, Prometheus, Grafana, Jaeger). Наведене обґрунтування логічно переходить до
Розділу 2, у якому виконується проєктування архітектури засобами C4 Model та UML.
