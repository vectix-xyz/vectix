# 🏛️ Архітектурна концепція екосистеми Vectix

## 📂 1. Організація Github / Turborepo (Monorepo)

Оскільки ви використовуєте **Turborepo**, найкращим рішенням є архітектура **Monorepo** (один репозиторій для всього проєкту). Це дозволить перевикористовувати TypeScript типи, валідаційні схеми (Zod) та конфігурації між різними додатками.

### Структура папок проєкту:

```text
vectix-monorepo/
├── apps/
│   ├── web-seo/            # 1. vectix (Next.js - головна сторінка, SEO)
│   ├── driver-app/         # 2. vectix.driver (SolidJS - додаток для водіїв)
│   ├── ticket-app/         # 3. vectix.ticket (Next.js - клон tickets.ua)
│   ├── corp-panel/         # 4. vectix.corp (Vite + React - B2B CRM панель)
│   ├── api-gateway/        # NestJS API Gateway
│   ├── ms-tickets/         # NestJS мікросервіс квитків
│   ├── ms-cargo/           # NestJS мікросервіс посилок
│   └── ms-logistics/       # FastAPI мікросервіс (алгоритми маршрутів та гео-дані)
├── packages/
│   ├── ui-shared/          # Спільні UI компоненти (за потреби)
│   ├── types-dtos/         # Спільні TS типи для фронтенду та NestJS
│   └── tsconfig/           # Спільні конфігурації TypeScript
├── package.json
└── turbo.json
```

> 💡 **Примітка щодо FastAPI (Python):** Оскільки FastAPI живе в екосистемі Python, його не вийде збілдити напряму через npm/pnpm. Проте Turborepo може запускати Python-скрипти або Docker-команди через звичайні скрипти в `package.json` всередині папки мікросервісу.

## 💻 2. Аналіз та вибір технологій для фронтенду

### 📱 Vectix.Driver ➡️ SolidJS

* **Ваш вибір:** 10 з 10.
* **Обґрунтування:** В умовах слабкого покриття мережі та бюджетних смартфонів водіїв, відсутність Virtual DOM у SolidJS забезпечить максимальну швидкість роботи інтерфейсу та мінімальне навантаження на процесор девайсу. Це критично для постійного фонового трекінгу геолокації.

### 🏢 Vectix.Corp (B2B SaaS-панель) ➡️ Vite + React

* **Рекомендація:** Замість SolidJS тут краще обрати **Vite + React + TS + Tailwind + shadcn/ui**.
* **Обґрунтування:**
  1. **Екосистема готових компонентів:** Для CRM потрібні складні інтерактивні таблиці (фільтрація, сортування), графіки аналітики та карти. В React є потужні готові інструменти: `TanStack Table`, `Recharts`, `React Leaflet`. У SolidJS багато речей довелося б писати з нуля.
  2. **SEO не потрібне:** Панель знаходиться за авторизацією, тому SSR (Next.js) тут зайвий. Звичайне SPA на Vite завантажиться один раз і працюватиме блискавично.

### 🎫 Vectix.Ticket (Клон tickets.ua) ➡️ Next.js (Server-Side Rendering)

* **Рекомендація:** Тільки **Next.js**. Чистий React (SPA) тут не підходить.
* **Обґрунтування:** Користувачі шукатимуть квитки через Google (наприклад: *"купити квиток Київ - Львів"*). Next.js згенерує сторінку конкретного маршруту на сервері, що дозволить пошуковим роботам повністю її проіндексувати для SEO-просування.

## ⚙️ 3. Архітектурний міст: Бекенд ⇄ Фронтенд

1. **Едпоінт-консолідація:** **NestJS API Gateway** виступає єдиною точкою входу (Single Point of Entry) для всіх чотирьох фронтендів. Клієнтські додатки не знають про внутрішню структуру мікросервісів.
2. **Міжсервісна комунікація:** Між Гейтвеєм та мікросервісами NestJS комунікацію краще реалізувати через швидкий **gRPC** або брокер повідомлень **RabbitMQ / Kafka** (особливо для черг створення ТТН та обробки платежів).
3. **Роль FastAPI:** Ідеально підходить для `Vectix.Drive` та `Vectix.Cargo`. Розрахунок гео-координат, оптимізація маршрутів та алгоритми розбивки посилок по багажних відділеннях на Python працюватимуть ефективніше завдяки математичним бібліотекам. Зв'язок із гейтвеєм можна побудувати через **gRPC** або **Redis Pub/Sub** для передачі координат водія в реальному часі через WebSockets.
